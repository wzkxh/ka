J) You wrote "It is not a constant expression." (about X=?10) -- not so, we'll change it.
And these parts in docs/discussions:
"Every variable starts as 0" (my forced but temporary decision) -- I doubt it now. If a variable used before an
assignment it should be an error.
And constants:
`function NAME(...)` -- there is no differences (const <-> var) for functions because functions that are defined
by stmt `function name(...) ...` are already constants - you can't assign anything to that `name` (!). So `NAME` or
`name` - it's the same for such functions (again, not vars like f=\x:=1). They are always const, they are all
scanned/parsed/defined in one pass before execution (or rather compilation) of the whole file again, so all the fns
are always defined. Is that what is called 'hoisting'?
Also this part:
  print SIZE_G  -- => 5  (a global constant exists from the start)
  SIZE_G = 5
I don't agree with this. Functions are defined with 1st pass, when 'execution' not started, it's acceptable (and should
be mentioned in doc). But constants (and vars) - they are not defined before 'execution' passed through them. So to see
this SIZE_G, the print statement must be after the assignment. It's easier in the global scope, but actually the same
inside functions. we can't deal with complicated cases - for them we should issue warning, probably. but for simple
cases, when constant is defined e.g. at the beginning of function, it's easily seen and should work. The same about
"constant expressions". we don't have full power on constexpr of C++ and we don't have separate pre-processing step,
like in C, so our constants are not like #define in C, they are really variables and their value can be result of
run-time function or ?10 - it is really calculated at run-time. It's just that this value is not supposed to be
changed later in some other code (or the same code :)) -- this is what we check, not that it's defined or not. And so
this is connected with initialized/uninitialized:

K) Uninitialized variables. I propose this: if it can be controlled during compile time - fine, do it and maybe mark
those variables/consts as safe (if you need such marking). if there are unclear cases (inside ifs/whiles, as parameters
etc), I propose 'initialization flags'. and this mode of compilation we'll have by default. that is, such 'unclear'
variable will have also hidden 'initialized' flag, which is initially (from the beginnig of its scope) false. an
assignment sets it to true, run-time. an access (reading) checks this flag (run-time) and reports error if it's not
initialized. clear?

L) And as for overflow checks, we'll eventually have different compilation modes (choosen by options of the compiler
and pragmas that we'll have soon, but not now) - in check-initializations mode we'll have such mechanism for parts
(whole file or a function) compiled this way, if this mode is off, then no such 'initialized' flags and vars/consts
are used as they are (in worst case, uninitialized, as it happens in C).
