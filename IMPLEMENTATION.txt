IMPLEMENTATION - decisions of the Kota language and compiler: what was chosen, why, what else was possible, what is open
=========================================================================================================================
Where things are:  README.md = the files and how to run.  LANGUAGE.md = what the language is (the user's view, short and exact).
This file = the internals worth knowing: decisions, reasons, alternatives, memory layouts, algorithms, known issues; it completes LANGUAGE.md.
LIBRARY.txt = the runtime routines as C.  NOTES.md = how the code is organised (Claude's own notes).
RELEASE_NOTES.md = what changed in which version (a list only).  PLANS.md = the owner's plans.
"User" below means the language designer (the owner of the project), "I" is Claude.
Section numbers are used in cross-references (LIBRARY.txt, NOTES.md, ...): 1 General, 2 Lexical, 3 Statements, 4 Expressions, 5 Types, 6 Strings, 7 Floats,
8 Scope, 9 Constants, 10 Assignment before use, 11 Absolute value and length, 12 Prime test, 13 Random numbers, 14 Time, 15 Command line and options, 16 Known issues.


1. General
----------
- The compiler writes the PE file itself (no assembler, no linker, no C compiler): no dependencies, one Python file, runs anywhere,
  the .exe runs on Windows x64. The price: all machine code is generated by hand-written byte sequences (verified with an emulator).
- Pure Python 3 in one file (kota.py). The only dev-time dependencies are for checking: unicorn + pefile (emulator), keystone-engine (only to
  rebuild the machine-code blocks of the runtime: tools/float_rt.asm, time_rt.asm, int_rt.asm). The compiler itself needs nothing.
- Code style: 2 spaces per indentation level in .py and .ko files (user decision). Brackets (user, version 6.3): if blanks are used between arguments, use them also after `(` and before `)`;
  in short cases (a few arguments, short names) use no blanks at all: `f(a,b)`, `fn(T1,T2)->R`. Same for `[]`. New code and docs follow it; old code is changed when that costs nothing
  (the notation of function types in messages was).
- Delivery as .zip. 7-Zip would be nicer but it is not installed in the sandbox and would have to be installed in every session.
- Tests are the definition of the language: expected outputs are derived by hand or by an independent reference (Python), not copied from
  the compiler's output. Twice a hand-computed expectation was wrong and the compiler right: always check which side is wrong.
  Test programs carry `-- =>` comments with the result of the statement (tools/annotate_tests.py adds them from the real behaviour).


2. Lexical decisions
--------------------
Comments: `--`, `--[[ ... ]]--` (inside one line), `--[[ ... --]]` (several lines; the rest of the closing line is ignored), and (version 6.1, user) `# text`.
  The user: hash followed by a space cannot occur anywhere else, so `#` can be overloaded; it makes Python-style comments usable. I also accept `#` at the end of a line (an empty comment line,
  editors strip trailing spaces) but never a `#` directly after a digit: `2#` is the start of a binary literal and `x = 2#` must stay an error instead of silently becoming `x = 2`.
  `1# comment` (glued to a number) is therefore an error. Hex literals `#ff` do not clash: the character after the hash is not a space.
  Wording (user, version 6.2): `# ` comments and `0x` literals are compatibility forms. They exist to ease the migration of existing programs and for copying code and constants
  between Kota and other languages (Python files above all); they are discouraged in new Kota programs, which should use `--` and `#ff` / `2#...`. The reference says so.
  The user asked for the inside-line form to stay on one line and said the rules were a minor issue. strip_comments() blanks comments before
  the lexer so that line numbers and columns stay right.
TAB: no special treatment (user decision, version 3). It is a character like ESC or `$`: text inside strings/comments, `unexpected character`
  elsewhere. Earlier (version 2) any TAB was an error; the simpler rule needs no code at all.
Identifiers: ASCII only. `and or not let global nonlocal input fn` are ordinary names (the words were removed from the language).
Numbers: `_` only between digits (user: no `__`, not at the start or end). Hex `#ff` (and, version 6.1, `0xff` / `0XFF`, so that constants copied from Python files work) and binary `2#1011` take all 64 bits
  and wrap to signed. A number that does not fit any form gives `bad number '...'`; the hint about `_` is shown only when there is a `_` in it, `0b101` gets the hint `2#101`
  (the first version of the message blamed `_` for every ill-formed token, e.g. `0xFFFF...`, which was wrong). Python's `0b` and `0o` are not accepted (Kota has `2#`, no octal).
  Only base 2 exists; radix 3..36 (`3#122`, `36#zzz`) is not implemented. `#'...'` is reserved for hex byte strings.
Floats: `digits.digits`, `digits.digits e sign digits`, `digits e sign digits` (user's list); no `.5`, no `1.`, no INF/NAN literals.
  `5e3` is a float. Specific error messages for the near-misses (`1.`, `.5`, `1e`, `1.5abc`, `1.5.2`).
Strings: `'...'` = byte string `str`, `"..."` = unicode string `text` (user). A `str` keeps the bytes as written (`^XX` is the raw byte, `^uXXXX` its UTF-8);
  a `text` keeps 32-bit code points (`^XX` is U+00XX). Both print as UTF-8 (the values and the runtime are in section 6).
  Escape char is `^` (not `\`) so that `\` stays free (it became the `function` synonym and integer division). `^uXXXX` and `^UXXXXXX` are the user's spelling.
  Joining of adjacent literals: a newline ends a statement, so `print "a"` NEWLINE `"b"` is two statements; inside parentheses newlines are ignored,
  so `print ("a" NEWLINE "b")` joins (user's example).
  The generated program calls SetConsoleOutputCP(65001) at start so that UTF-8 shows correctly; the console keeps that code page afterwards (restoring it was not worth the code).
Keywords: `function` with the synonym `\`, `skip` (empty statement), `elif`, `assert` (7.2); `fn` is gone. A one-parameter function needs no parentheses
  (`function f x: ...`, `\x: =x+1`): `function name x` is a definition, `function x:` a literal; decided by two tokens of lookahead.
Operator spelling is the user's: `+>` arithmetic shift right, `<*` / `*>` rotate, `?` and `!` for the conditional (`!` because `:` starts blocks),
  `@x` for variables of the enclosing function (temporary, user expects to redo it).


3. Statements and blocks
------------------------
- Statements end at the end of the line; `;` is optional wherever the next token cannot continue the statement (keyword, `{`, `)`, `}`, `else`).
  User: "`;` is really needed only to separate statements on the same line". A line ending with an operator, `=` or `,` continues.
- One-line bodies (`if a: b; c`) run to the end of the line and nest; `else`/`elif` bind to the nearest `if` that can still take one, also across lines.
  Alternative considered: bind by indentation. Rejected as too elaborate; braces can force the other meaning.
- `{ ... }` is an ordinary statement (user, version 3). First there was a special case "`:` followed by `{`"; the user called it a mistake and asked for the
  general rule. Consequence: in `if a: {b} c()` the `c()` belongs to the body (the body runs to the end of the line), in `if a {b} c()` it does not.
- `=` at the start of a statement is a short `return`. Function bodies have no expression form and no implicit result (`fn f(x) x*x` was removed);
  a bare expression statement that is not a call can get a warning (typical mistake `{m = 2*n; m}`); it is off by default, see section 15.
- After the removal of `let`, `global`, `nonlocal`, `input`: no way to read input for now ("it's ok for now").

- One-line bodies and `?!` (version 6.4): the first rule was "a one-line body runs to the end of the line or to a closing `)`, `}` or `,`", made to ease parsing. The user pointed out that the proper
  rule is "to the end of the expression the body belongs to", which depends on the context. The contexts that end an expression early are the brackets (`)`, `,`, `}`) and the middle part of
  `c ? a ! b`, which ends at its `!`. The parser keeps a stack of the open contexts (`ctx`); the middle part pushes `?`, and `end_stmt` / `at_end` accept `!` when it is on top. The else part
  ends at the end of the line like any other expression, and a `?!` inside the body consumes its own `!`. Parentheses are no longer needed around function literals in the middle part.

- `assert condition[, report]` (version 7.2, user): the condition is any expression, false is `0`, `0.0`, `''`, `""` (the same truth rule as `if`); if it is false the report is shown, or the condition when there is no report,
  and the program ends with exit code 1. The user's wording: "report the second expr if provided, if not provided just say that the condition failed (maybe also print the condition)".
  - Output (my choice, easy to change): to standard output like the runtime errors, one line `assertion failed (line N): REPORT`. The report is one `print` item (an int, float, str or text; a function is a type error)
    and is evaluated only when the assert fails. Without a report the condition is printed, rebuilt from its tokens (`render_tokens`: spaces normalised, numbers in decimal, `0xFF` shows as `255`; nothing if the condition
    does not stand on one line). N is the line of the keyword.
  - Done by a rewrite in the parser, not as a new statement: `assert c, r` is `if !c: print "assertion failed (line N): ", r; exit 1`. The checker, the initialisation analysis and the code generator needed no change;
    type errors of the condition say `in 'assert'` (the `not` node carries that text), those of the report `in 'print'`.
  - `CHECK_ASSERTS` (a constant at the top of kota.py; the user asked for "a global var at the beginning like CHECK_ASSERTS"), True by default. False: the statement is parsed (syntax errors are still found, names are
    still resolved) and dropped, so its expressions are neither type-checked nor evaluated, like Python's `-O`. A program can therefore compile with the flag on and fail to compile with it off only through a type error inside an assert.
  - `assert` is a keyword: it cannot be a variable or function name.
  - Tests: `74_assert` (passing asserts, report not evaluated, one-line body, continued lines), `rt_assert_*` (message, condition text, int and float reports, empty text, in a function), `err_type_assert_function`.
    `CHECK_ASSERTS = False` was tried by hand; there is no test for it (it is a compiler constant).


4. Expressions
--------------
Precedence (user wanted few levels, "C programmers always use parentheses"):
  - Bit operators sit between `+` and the comparisons, in C's order (`&` over `~` over `|`) but ABOVE `==` and `<`, so `a & 1 == 0` means `(a & 1) == 0`.
    The user said "like in C, I guess" about the order among them; the position relative to comparisons is my choice (Python-like) because C's
    position is a well-known trap. One table row to change if exact C is wanted.
  - Shifts and rotates are one level between `&` and `+` (as in Python/C relative to `+`).
  - Unary operators bind tighter than `^`: `-2^2` is 4 (user, version 3). `^` is right-associative (`a^b^c = a^(b^c)`, user).
  - Chained comparisons (`a < b < c`) within `== !=` and within `< <= > >=`, not mixed (user); the middle operand is evaluated once, stops at the first false link.
  - Conditional `c ? a ! b`: lowest precedence, right-associative, only the chosen branch runs. `!` followed by `=` is always `!=`.
    (Since 6.4 a one-line function body in the middle part ends at the `!`, see section 3.)
`^` is power after an operand and the global-variable prefix where an operand is expected (`print a ^b` is a power). Same trick for `\`: function
  where an operand/statement starts, integer division after an operand; for `?` (conditional / random, section 13), `|` (bitwise or / absolute value, section 11) and `*` (multiplication / prime test, section 12).
  The unary operators `- ~ ! ? | *` are one level, tighter than `^`: `|x + 1` is `(|x) + 1`, `-2^2` is 4. Consequence: a function definition can no longer follow a complete statement
  on the same line without `;` (it used to, as `\` was a statement start), see version 6.
Integer power with a negative exponent is a runtime error (simplest; the real result is not an integer).
Shifts (user's spelling and rules):
  - `<<` shift left; `>>` logical (unsigned) right; `+>` arithmetic (signed) right; `<*` `*>` rotate. An arithmetic shift left has no operator: it is the same
    as `<<` (user asked; yes).
  - A count of 64 or more shifts everything out (0, or the sign for `+>`). The code compares the count with 63 (unsigned compare); x86 would otherwise
    take the count modulo 64. Rotates use the hardware behaviour, count modulo 64, which is the natural definition.
  - Negative counts (version 6, user): shift the other way (`x >> -n` is `x << n`, ...). For rotates this is automatic (modulo 64).
    Before version 6 a negative count shifted everything out.
Chained assignment (version 7.5, user): `a = b = c = e` is parsed as `c = e; b = c; a = b` (a `block` node; `e` is computed once, the last name is set first, like C). Every name goes through the normal assignment rules (constants, `^x`, `@x`,
  types: a mismatch is reported for the name that cannot take the value). Only plain `=` chains; `a = b += 1` is not a chain.
Unary plus (version 7.5, user): `+x` is a unary operator of the level of `-`; for numbers it is the identity, for `str` and `text` it makes the upper-case string (a new object, the empty string stays 0). The result has the type of the operand
  (as for `?x`). `str`: ASCII a-z only (bytes are bytes; UTF-8 in a `str` is left as it is). `text`: a table of simple one-to-one mappings (ASCII, Latin-1, Latin Extended-A, Greek, Cyrillic: tools/int_rt.asm, `upper_table`,
  checked against Python's `upper()` for these blocks); letters whose upper case has several characters (`ß`, `ŉ`) and other scripts are copied unchanged. The user: English letters are the point, the rest is a bonus.
Compound assignment `x op= e` is sugar for `x = x op e` done in the parser (`&&=`/`||=` become and/or nodes, so they short-circuit). Targets `name`, `^name`, `@name`.
  A consequence of the type rules: `x /= 2` on an int variable is an error since `/` gives a float; use `\=`.
Division (version 6, user): `/` is always float division, `\` always integer division. Before version 6 `/` truncated for ints and gave a float for floats,
  so the result type depended on the operand types; two operators make the type of each operation fixed.
Floored division and modulo (version 6.2, user: "let's do it mathematically"): `a \ b` = floor(a / b) (rounds toward minus infinity), `a % b` has the sign of `b`,
  and `a \ b * b + a % b == a` always holds for ints (for floats up to rounding, as in J and Python: (-7 \ 3.2) * 3.2 + -7 % 3.2 is -7.000000000000001); `7 % 3 == 1` and `-7 % 3 == 2` because 7 - 1 and -7 - 2 are divisible by 3. Versions 6 and 6.1 truncated toward zero (C and the
  machine instruction idiv): then `-7 % 3 == -1`, and a remainder can be negative for a positive divisor, which is rarely what a modulo is used for (indexes, wrapping, ranges).
  This is also what Python does, so numbers agree with it. Implementation: the machine division truncates; the result is corrected when the remainder is not 0 and its sign differs from
  the divisor's: the quotient becomes one less, the remainder bigger by the divisor. For floats the same correction is applied to the exact C-style fmod remainder
  (rt_fmodfloor); a zero remainder is returned as +0.0 (the sign of a zero would only be noise). Float `\` = (a - fmod(a, b)) / b minus one when the remainder was corrected,
  rounded to the nearest integer: a - fmod(a, b) is mathematically a multiple of b, but the subtraction itself can round, so the quotient may come out as 13276.999999999998;
  truncating it (versions 6 and 6.1 did) gave 13276 instead of 13277 in rare cases. A quotient outside the int range gives the smallest int (what the hardware conversion returns);
  making that an error would need a new message and a check, and explicit conversions do not exist yet anyway. Above 2^53 the float quotient is not exact.
  The tests check the identity for all pairs of small ranges, and a randomised comparison with Python's // and % (3000 cases, ints and floats) found no difference.


5. Types and the checker
------------------------
- Static, inferred, no annotations: int, float, str, text, function. A variable keeps the type of its first value; a parameter gets its type from the body and the calls;
  one signature per function (monomorphic). User: "calling fn f(a){} with an int makes it f(int), so calling it with f(f) is an error".
  Alternative: per-call polymorphism. More work, little gain (all values are one machine word anyway).
- Recursive function types are allowed (`a(a)`): no occurs check; unification skips pairs it is already comparing; messages cut cycles with `...`.
  The restriction was a limit of my first checker, not a safety rule: no int is ever called.
- Return types: all `return` expressions must agree; bare `return` and falling off the end are not checked (user: "don't deal with it for now").
  Hole: a function that returns a function on one path and falls off the end gives a null function; calling it is the runtime error "call of an unset function".
- Int and float mix only inside operators (user: "ops with int and float - convert both to float"): `+ - * % ^` give float if either side is float, `/` always float,
  `\` always int, comparisons compare as floats, `?:` promotes its branches.
  Assignment, call arguments and `return` are strict: no implicit conversion. So `x = 0` then `x = 0.5` is an error, `f(1)` and `f(1.5)` cannot both be called.
  Pros: nothing happens behind the user's back, the checker stays simple. Cons: annoying (`x = 0.0`). Relaxing assignment (int widens to float) is a one-line change
  in Checker.stmt if wanted; explicit conversions do not exist yet.
- The result type of an operator can depend on parameter types that a later call fixes, so plain unification is not enough. The checker records such
  operators as constraints (arith, eq, order, cond, num, abs) and settles them when operand types become known; whatever is unknown at the end becomes int
  (Checker.step / solve / finish). The code generator needs every expression's type to choose int or float instructions, so Checker.types maps
  id(node) to the type.
- Runtime arity/not-a-function checks were removed (the checker does it). The null check of a call stays (unset function variable).
- Truth: `0`, `0.0`, `-0.0` false, NaN true; the empty string false, any other string true (user; the values of strings are in section 6).
  A function is true unless it is unset (version 7.5, user: "any fn not zero must give true; we don't have 'null' yet"): a closure pointer is tested like any word (`test rax,rax`), so only the checker changed
  (`need_num(..., "truth")` in the conditions of `if`, `while`, `?!`, the operands of `&&`, `||`, `!`, and so `assert`, which is an `if !c`). `print` and `?` still refuse functions.
- A function has one signature, so the same function called with arguments of different types is an error: `f(1)` then `f('a')`, `f('a')` then `f("a")`, int then float and so on, in both orders
  (`in argument N of the call: expected X, found Y`; the tests are `err_type_arg_*`). Monomorphic by decision, see the first bullet.


6. Strings (version 6.8)
------------------------
- Two types (user): `str` is a byte string with the literal `'...'`, `text` is a unicode string with the literal `"..."`. Literals and escapes: section 2.
- Memory (the user's design): a value is one 64-bit word, the address of an object `[u64 length][contents]`. The empty string is the address 0: it needs no memory and no special case in assignment, calls, returns or closure boxes.
  A `str` object holds the bytes (the length counts bytes; a zero byte is allowed; no terminator), a `text` object holds 32-bit code points (the length counts characters, so indexing a text will be simple).
  Only the address is copied; strings are immutable and shared; nothing is freed (user: "only allocation, no freeing, no GC").
- Literals are static objects in `.data` (8-aligned). `+` makes a new object with `rt_alloc` (`rt_strcat`, `rt_textcat`); a concatenation with an empty result is 0.
- `str` and `text` never mix (user: "str + text doesn't work without conversion"); conversions are not there yet.
- Truth (user): the empty string (address 0) is false, any other string true: the same `test rax,rax` as for an int.
- Comparisons (Gemini added them, the user kept them) compare contents: `str` by unsigned bytes, `text` by code points, a shorter prefix is smaller (`rt_strcmp`, `rt_textcmp` give -1/0/1; the code generator turns that into 0/1).
  The checker has an `order` constraint (like `eq`) for `< <= > >=`, because two operands of unknown type may turn out to be strings.
- Printing: a literal item of `print` is written straight from `.data` (one write); any other item is an expression (`rt_print_value_str`, `rt_print_value_text`). A `text` is encoded as UTF-8 into a 1024-byte buffer on the stack
  and `WriteFile` is called when the buffer is nearly full and at the end (version 6.8.1; before, once per character). The program calls `SetConsoleOutputCP(65001)` at start so that UTF-8 shows correctly;
  the console keeps that code page afterwards (restoring it was not worth the code).
- `rt_alloc` checks the result of `HeapAlloc` (version 6.8): 0 is the runtime error `out of memory`, exit code 1. It covers closures and strings.
- Origin: Gemini implemented strings on top of version 6.3 (its 6.4 `str`, 6.5 comparisons and concatenation, 6.6 `text`). The user kept my 6.4 as the base; version 6.8 is that base with Gemini's string code merged in:
  the parser, the checker (`order`), the code generator and the hand-assembled routines `rt_strcmp`, `rt_strcat`, `rt_textcmp`, `rt_textcat`, `rt_print_value_str`, `rt_print_value_text`.
- Tests: `65_byte_string_values` to `72_long_text_print`, `err_text_str_*`, `err_type_str_*`. Only the operations above exist: no length function (see `|x`, section 11), indexing, slices or conversions yet.


7. Floats
---------
- A float is the bit pattern of a double in the same 64-bit slot as an int; nothing changes for variables, arguments, results, closures.
- Zero divisor: float `/`, `%`, `\` by zero (also -0.0) is a runtime error, like ints. IEEE would give inf/nan; there are no INF/NAN literals yet,
  so the error keeps them out of normal programs. Overflow still produces inf, `inf - inf` is nan; they print as `inf`, `-inf`, `nan`.
  Comparisons are exact (user: "let it be precise for now"); with NaN everything is false except `!=`. A tolerance for comparisons does not exist.
- `%` on floats is floored (sign of the divisor, see section 4); its core is C fmod, implemented as an exact integer shift-and-subtract algorithm (the musl algorithm)
  instead of x87 `fprem`, because the emulator (QEMU) emulates fprem approximately and the tests would then depend on emulator quality.
- `^` on floats: integer-valued exponent: x87 square-and-multiply in extended precision, rounded once (any base, negative exponents give 1/x^n).
  Fractional exponent: x87 fyl2x / f2xm1 / fscale, base must be positive (a negative base is a runtime error with its own message). 0^negative is division by zero.
- Printing (user: "some good formatting like in APL, J, maybe latest Python"): at most 15 significant digits, trailing zeros removed, `.0` kept so that a float
  never looks like an int, fixed notation for 1e-4 <= |x| < 1e15, else d.ddde+XX (Python style). `0.1 + 0.2` prints `0.3` (APL-like, hides binary noise);
  Python's repr would print 0.30000000000000004. Exact shortest-round-trip printing needs big-number arithmetic or Ryu tables: too much for now.
  The digits are made in x87 extended precision (N = round(x * 10^(14-e10)), 10^k by repeated squaring). Known limitation: when the 16th digit is very close to 5
  the 15th digit can be off by one, roughly 1 case in 10 000; the fuzz run (3000+ values, random bit patterns, denormals, boundaries) found none.
  The format is provisional (precision, width and layout control do not exist yet).
- The routines (rt_fmt_float, rt_fpow, rt_fmod) are machine code generated from tools/float_rt.asm by tools/build_float_rt.py (Keystone assembles single
  instructions; the script does labels and jumps because Keystone hung on larger inputs). They set the x87 control word to extended precision themselves:
  Windows starts processes with 53-bit precision, which would break the digit generation. The emulator starts with 64 bits and would hide that.
- Verification: tools/fuzz_float.py runs the routines in Unicorn against Python (format, fmod: exact; integral pow: within 1 ulp). The emulator computes fyl2x/f2xm1 only to
  about 4e-15, so fractional powers are the least verified part on real Windows; tests with fractional exponents use values whose 15 digits agree.


8. Scope, functions, closures
-----------------------------
- Globals via `^x` (user: `global x = e` is not pretty, `^x = e` is). A name cannot be both local and `^x` in one function; the user dropped the idea of
  shadowed globals ("having ^x for read/write globals and x for locals doesn't seem ok"). `^x` at the top level equals `x`. `function ^name` was refused ("too much").
- `@x` = variable of the nearest enclosing function (draft, replaced the first spelling `\x`). A first version of the idea was `nonlocal x`. The user expects to
  redo it ("we'll do later"); only one level exists.
- Named functions are hoisted (created at scope entry): they exist from the start of their scope ("main code first, helpers below", mutual recursion). Version 6.4 (user): a name defined with
  `function` is a constant, "in a compiled language you cannot redefine a function with the same name or write f=2 after \f():=1" (Python allows it silently because a session is interpreted).
  Before 6.4 such a name was an ordinary variable that could be reassigned (test 20 did it); the check is made in Checker.stmt: the target's scope must not have a function of that name.
  The user also considered a single `f = function...` form instead; rejected (no main-first layout, call-before-definition becomes a runtime error, mutual recursion gets fragile).
  The names of functions are not special in other ways (no capital-letter rule); direct calls without a closure lookup remain a possible optimisation.
- Variables do not start as 0 for the program: reading one before its assignment is an error (section 10). The memory is still zeroed.
- Closures capture by reference through heap boxes; nothing is ever freed (no GC): accepted for now.
- Calls: own convention (arguments pushed left to right, closure pointer in rax checked for null, callee pops). At most 20 parameters (user: 100 is too many for humans
  and too few for splitting an array).


9. Constants (version 4; rewritten in version 6.4)
--------------------------------------------------
User's idea: an identifier of capitals (digits, `_`) is a constant: it gets its value when created and cannot be assigned elsewhere; main purpose top-level parameters.
Version 4 made them compile-time-like (a constant expression as the value, created at scope entry like named functions). The user corrected this in 6.4: a constant is
really a variable that is assigned at run time; it is only not supposed to be changed later, and that is what is checked. So now:
- Name rule: at least one capital letter, no lowercase letters (`MAX_SPEED`, `X2`, `_N`). Parameters with such names are rejected.
- Where: directly in the statements of the program or of a function body; not inside if/elif/else/loops/blocks (a loop would run the same code again, an `if` may not run it).
  The scope of a function constant is that function and the ones nested in it. A constant cannot be written `^X` or `@X` inside a function; a function may define a constant
  with the name of a global one (like any local). Any second assignment, also `X += 1`, is an error.
- Value: any expression, also a call or `?10`; it is computed when the line is reached. Nothing is hoisted any more and there is no constant-expression rule. Reading a constant
  before its line is the same error as for every variable (section 10), which closed the old problem of a function seeing a half-set constant.
- `function NAME(...)` is not special: every name defined with `function` is a constant (section 8); the capital-letter rule only concerns assignments.
- Implementation: the assign node still has a sixth element True, which only marks a definition for the checks in the parser.


10. Variables are assigned before they are read (version 6.4)
-------------------------------------------------------------
User's decision: a variable used before an assignment is an error; "if it is clear at compile time, say so then; where it is not clear, use hidden initialization flags";
globals that are defined at the top of the program and then used in functions "need no flags, it is clear that they are defined". Different modes (flags on or off) are for later,
chosen by compiler options and pragmas; the code has the constant CHECK_INIT (True) for it. The former rule "every variable starts as 0" is gone: it hid mistakes.
Three outcomes for every read (class InitCheck, a pass after the type checker, before code generation):
  assigned on every path        -> nothing is generated;
  assigned on no path           -> compile error (the old messages: "variable 'x' used before assignment", "variable 'x' is local to function 'f' and used before assignment ...");
  assigned on some paths only   -> the variable gets a hidden flag; the read checks it; a failed check ends the program: "runtime error: variable 'x' is not initialized" (exit code 1).
The analysis is the usual definite-assignment one, per scope, in the order of execution, with two sets per point: `must` (assigned on every path) and `may` (on some path):
- an assignment adds the target to both; `if` joins its branches (must: intersection, may: union; a branch that ends in return/break/continue/exit does not count);
- `while`: the condition and the body see `may` widened by everything the body assigns (a later iteration may have assigned it); after the loop `must` is the old one;
- a call: after it, `may` also contains the variables that some other scope assigns (`^x`, `@x`); a call is also recorded as a "call site" with the current `must`;
- parameters and `function name` definitions are in `must` from the start of the scope; `return` records an "exit" with the current `must`; so does the end of a function body.
A variable of another scope (a global read in a function, a variable of the enclosing function read by a nested one) is judged afterwards: code of a scope can only run after a call
(or after the function was left), so the variable needs no flag if it is in `must` at every call site of its owner scope, and for a function also at every exit of it. In the
typical program the globals are assigned at the top, before the first call: no flags, no cost (the eight programs in performance/ have none). The rule is conservative: a call of an
unrelated function before the global is assigned makes the flag necessary. A variable that is not provable gets: a data slot (global), a frame slot (local) or the second quadword of its
16-byte box (captured variable), set to 1 by every assignment, also one made from another scope; the read is `mov rax,[flag]; test rax,rax; jz stub`. One stub per variable name prints
the message and ends the program. The cost is about three instructions per checked read.
Alternatives considered: a warning for the unclear cases (rejected by the user in favour of flags); a special "unassigned" value (impossible: every 64-bit value is valid); a flag for every
variable (slower, and unnecessary).
Known approximations: any call widens `may`, also one that cannot assign the variable; two assignments in different branches of a loop count as "maybe"; `exit` and `return` end a path.


11. Absolute value and length: unary | (version 7.3)
----------------------------------------------------
- `|x` (user): the absolute value of numbers, the length of a `str` or a `text`. It is a prefix operator on the level of the other unary operators (`|x + 1` is `(|x) + 1`). There is no closing bar (`|a - b|` would clash with
  bitwise or), so a difference needs parentheses: `|(a - b)`. After an operand `|` is bitwise or as before, so `6 | |-1` is `6 | (|-1)`. `||` is one token (logical or): two bars in a row, `|(|x)`, need a space or a bracket.
- Result type: int -> int, float -> float, `str` and `text` -> int. The operand type may still be unknown while a function body is checked (a parameter), so this is a constraint like `+` (`abs` in `Checker.step`):
  it is settled when a call gives the parameter its type; if that never happens, int. A function operand is the error `in operand of '|'`.
- Int: `(x ^ (x >> 63)) - (x >> 63)` with an arithmetic shift; the smallest int has no positive counterpart and stays negative (arithmetic wraps everywhere in the language).
  Float: the sign bit is cleared (`btr rax,63`), so `|-0.0` is `0.0` and a NaN stays a NaN.
- Length: the first 8 bytes of the object (section 6): bytes for a `str`, code points for a `text`; the empty string is the address 0 and has length 0, so it is one test and one load, no call.
- Tests: `76_abs_length`, `err_type_abs_function`.


12. Prime test: unary * (version 7.4)
-------------------------------------
- `*n` (user): 1 if the int n is prime, else 0; ints only (a float or a string is a compile error that names `'*'`). A prefix operator on the level of the other unary operators; after an operand `*` is multiplication
  as before, so `3 * *5` is 3 and `**7` is `*(*7)` = 0 (there is no token `**`).
- The algorithm is the user's: a 64-bit table for n < 66, then 2 and 3, then trial division by i and i + 2 for i = 5, 11, 17, ... while i * i <= n. It is machine code (`rt_isprime`, tools/int_rt.asm, LIBRARY.txt section 9).
- The user asked me to check the function for -2..100 first. The constant of the request, 0x28208A20A08A28AD, was wrong for the lookup `(mask >> (n - 2)) & 1`: it has the bit for each prime p at position p (and a stray bit 0),
  which is the right mask for `mask >> n`, shifted by two plus one bit; with it 4, 9, 15, 21, ... came out prime. The mask for `(n - 2)` is 0x0A08228828228A2B (bit k is set iff k + 2 is a prime; 18 bits).
  With that constant the function agrees with a sieve for -100 .. 300000 (Python) and with a Miller-Rabin test on the numbers of tools/fuzz_prime.py (run in the emulator through the compiled operator).
- One change to the user's code: `i * i <= n` is checked for signed overflow. The largest i of the form 6k - 1 below the root of the largest int is 3037000499 and the next one, 3037000505, squares to more than the largest int;
  with wrapping arithmetic that square is negative, the loop would go on, and for the primes in [3037000499^2, largest int] (the largest is 9223372036854775783) it would run some 4 * 10^8 steps more before the wrapped
  square gets large again. The overflow flag of `imul` ends the loop at once (the answer is "prime" then).
- Speed: about sqrt(n) / 3 steps with two 64-bit divisions each. A prime near 2^63 needs 5 * 10^8 steps, several seconds on a real machine. A Miller-Rabin test for 64 bits would be about a thousand times faster; only
  worth doing if it is needed.
- The user's rule: no prime test of big numbers (10^12 and larger) in my tests, in tools/fuzz_prime.py or by hand, because trial division is slow there; they stay below 10^9. The overflow guard was checked once, before that rule,
  on 9223372036854775783: the answer 1 came after 5 * 10^8 steps (173 s in the emulator). The user's own test `78_primes` has the large numbers and runs on Windows.
- Tests: `77_prime` (the numbers -2..100 one by one, the primes below 100000 counted, a comparison with a trial division written in Kota), `78_primes` (user), `err_type_prime_float`, `err_type_prime_text`.


13. Random numbers (version 6.3)
--------------------------------
- Algorithm and state: SplitMix64 (the user's C code) with the initial state 0x123456789ABCDEF0, set at the start of every program: until a program sets the state itself, its random numbers are always
  the same. `?n` is the next 64-bit number modulo `n`; the float is `(next >> 11) * 2^-53 * x`, replaced by the next smaller float if it is not below `x`.
User's design: a unary operator `?x` on numbers; the algorithm is the user's C code (SplitMix64 with next_u64, rand_int64, rand_float64), translated to machine code.
- `?n` (int n > 1): next_u64 % n (as unsigned numbers), so 0..n-1. The modulo bias is accepted, as in the C code. `?1` was a runtime error in 6.4 ("for the future"); since 6.9 it is the time (section 14).
- `?0`: the next 64 bits as a signed int. `?m` (int m < 0): the state becomes -m and the result is 0: "half the range, not all cases, but it's ok" (a seed is
  a positive 63-bit number; for the smallest int the negation wraps to 2^63, so that case is also a valid state).
- `?x` (float x > 0.0): ((next >> 11) * 2^-53) * x, which is exact for the 53-bit part; if rounding made the result reach x it becomes nextafter(x, 0.0) (the number below x,
  i.e. one less in the bit pattern). Version 6.4 (user): `?0.0`, a negative float and NaN are runtime errors ("bad argument of '?'"); before, the C code was followed literally.
- Determinism (user): the state at the start of every program is the constant 0x123456789ABCDEF0, so a program always gets the same numbers (useful for tests). The user plans a time() later
  and then the seed can come from the clock: "when we implement time(), we'll see". The state is 8 bytes in .data (offset 0x40), its initial value is written into the data image by build_pe.
- Parsing: after an operand `?` is the conditional operator, where an operand is expected it is the unary random operator (the same trick as for `^` and `\`). It binds like the other unary
  operators (tighter than `^`). `??5` works (the inner number is the argument). Type: the type of the operand (int -> int, float -> float), decided at compile time.
- The three routines (rt_next_u64, rt_rand_int, rt_rand_float) are hand-assembled in kota.py like the rest of the runtime, not generated from float_rt.asm. `?x` as a statement is an ordinary expression
  statement (no warnings are issued by default). `?x` may be used in a constant (user, 6.4: a constant is a variable assigned once at run time).
- Tests: tests/62_random.ko. The expected numbers come from an independent Python version of the C code, not from the compiler.


14. Time (version 6.9)
----------------------
- `?1` is the UTC time in microseconds since 1970 (user): `GetSystemTimePreciseAsFileTime` gives 100 ns units since 1601; minus 116444736000000000, divided by 10 (user). It needs Windows 8 or newer.
- `?'fmt'` / `?"fmt"` is the local time (`GetLocalTime`: the milliseconds are all the precision there is, so F3 is exact, F1 and F2 are cut, not rounded) as a `str` / `text` of the same kind as the argument.
  The codes are a letter and a digit, everything else is copied (user). `?` accepts every operand type that `!` accepts, and `?x` has the type of `x`.
- Design (the user's suggestion): one engine works on text. `rt_time_format` writes at most 64 code points into a buffer on the stack (user: "some reasonable length, e.g. 50 or 64"; a code that does not fit ends the result,
  an unfinished code is never half written). A `str` format is first converted to text (`rt_utf8_to_text`, at most 128 code points, which is enough because every format character gives at least half a result character),
  and the result is converted back (`rt_text_to_utf8`). The conversions work between two buffers that exist already; the allocation is separate (`rt_time_text`, `rt_time_str`). An empty result, or no format at all (0),
  gives 0 and allocates nothing.
- A byte of a `str` format that is not valid UTF-8 would be lost by a plain conversion. So the decoder maps it to U+DC00 + byte (Python's surrogateescape) and the encoder maps U+DC80..U+DCFF back to that byte:
  the byte survives. Such surrogates exist only inside these two buffers (a `text` literal cannot contain surrogates).
- The routines that only compute are machine code from tools/time_rt.asm (TIME_RT in kota.py, built by tools/build_float_rt.py like the float runtime; the script got `db` and `lea rax,[rip+label]` for it).
  The three that call Windows or allocate (`rt_time_us`, `rt_time_text`, `rt_time_str`) are hand-assembled in kota.py. `rt_alloc` is shared with closures and strings (section 6).
- Tests: the real clock cannot be compared in a test, so `73_time` checks ranges, shapes and the parts that do not depend on the time. tools/fuzz_time.py checks the formatting exactly against a Python reference at fixed times
  (the emulator takes the time as a parameter): random and edge-case formats, `str` and `text`, 6 times.


15. Command line and compile-time options (versions 7.1, 7.2)
-------------------------------------------------------------
- `-e` (7.1, user): compile, run the .exe, delete it. The exit code of kota.py is the exit code of the program, so it can be used in scripts. `-k` keeps the .exe and says `kept NAME` on stderr (the output of the
  program stays alone on stdout); `-k` without `-e` or `-c` is a usage error. `-c TEXT` works like Python's: the source is the text, nothing is read; it implies running; a source file together with `-c` is a usage error.
- `-c` is done internally (the user offered "a temp file or all internally"): no `.ko` file is made. Errors and warnings are named `<command>`; line numbers count the lines of the text.
- Where the .exe goes: with `-e` or `-c` and neither `-k` nor `-o`, a file in the system's temp directory that is deleted after the run, so an existing `program.exe` next to the source is never overwritten or deleted.
  With `-k` the usual place: next to the source, or `yyyymmdd_HHMMSS.exe` in the current directory for `-c` (the user's example name). `-o NAME` names it in every case; without `-k` it is deleted after the run all the same.
- A compile error runs nothing and leaves no file. The .exe is also deleted when running it fails. Running is only possible on Windows: elsewhere the message `cannot run a Windows .exe on this system` and exit code 1
  (Wine was not tried). The message `wrote NAME (N bytes)` is printed only when nothing is run. Test: tools/test_cli.py (the emulator stands in for Windows).
- Constants at the top of kota.py (the user: modes "are for later, chosen by compiler options and pragmas"):
  - `CHECK_INIT` (True): the hidden flags of section 10; False removes them.
  - `WARN_UNUSED_VALUE` (False): the warning for an expression statement that is not a call (section 3).
  - `CHECK_ASSERTS` (True): `assert` statements (section 3).
- `VERSION` is a constant in kota.py; there is no option to print it (the user asked for none).
- A source file that cannot be read (missing, a directory, no permission) gives `NAME: error: cannot read the source file: REASON` and exit code 1 (version 7.5; it was a Python traceback).


16. Known issues and limitations
--------------------------------
- I can only check with an emulator (Unicorn): the x87/SSE float routines, the Windows calls and the UTF-8 console output are verified on real Windows by the user's runs of the test suite (the latest report is in RELEASE_NOTES.md).
- The 15th digit of printed floats can be off by one in about 1 case in 10 000. Fractional float powers are only checked against an emulator that is less accurate than the FPU.
- Float `\` with a quotient outside the int range gives the smallest int silently. `-9223372036854775808 \ -1` raises a hardware exception (not handled).
- The compiler stops at the first error. The unused-expression warning exists but is off by default (version 6.4, section 15; the user: "keep in mind that there can be such a warning, but do not issue it now"); it is simple: any non-call expression statement.
- Falling off the end of a function is not type-checked (see 5). Deep recursion (about 10 000+ levels) overflows the 1 MB stack and crashes.
- A function definition cannot follow a complete statement on the same line without `;` (version 6, see 4).
- Memory is never freed (closures, strings).
- Strings can only be made by literals, `+` and `?'...'`; there are no conversions between `str` and `text`, no indexing, no input (section 6).
- The prime test is trial division: slow for numbers above 10^12 (section 12). The time needs Windows 8 or newer (section 14).
- With `CHECK_ASSERTS = False` the dropped asserts are not type-checked (section 3).
- Upper case (`+s`): only the letters named in section 4 change; no full Unicode case mapping.
