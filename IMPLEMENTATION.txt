IMPLEMENTATION - decisions of the Ka language and compiler: what was chosen, why, what else was possible, what is open
=========================================================================================================================
Where things are:  LANGUAGE.md = what the language is (short, exact).  NOTES.md = how the code is organised (for Claude).
RELEASE_NOTES.md = what changed in which version.  PLANS.md = the owner's plans.  This file = the reasons.
"User" below means the language designer (the owner of the project), "I" is Claude.


1. General
----------
- The compiler writes the PE file itself (no assembler, no linker, no C compiler): no dependencies, one Python file, runs anywhere,
  the .exe runs on Windows x64. The price: all machine code is generated by hand-written byte sequences (verified with an emulator).
- Pure Python 3 in one file (ka.py). The only dev-time dependencies are for checking: unicorn + pefile (emulator), keystone-engine (only to
  rebuild the float runtime). The compiler itself needs nothing.
- Code style: 2 spaces per indentation level in .py and .ka files (user decision). Brackets (user, version 6.3): if blanks are used between arguments, use them also after `(` and before `)`;
  in short cases (a few arguments, short names) use no blanks at all: `f(a,b)`, `fn(T1,T2)->R`. Same for `[]`. New code and docs follow it; old code is changed when that costs nothing
  (the notation of function types in messages was).
- Delivery as .zip. 7-Zip would be nicer but it is not installed in the sandbox and would have to be installed in every session.
- Tests are the definition of the language: expected outputs are derived by hand or by an independent reference (Python), not copied from
  the compiler's output. Twice a hand-computed expectation was wrong and the compiler right: always check which side is wrong.
  Test programs carry `-- =>` comments with the result of the statement (tools/annotate_tests.py adds them from the real behaviour).


2. Lexical decisions
--------------------
Comments: `--`, `--[[ ... ]]--` (inside one line), `--[[ ... --]]` (several lines; the rest of the closing line is ignored), and (version 6.1, user) `# text`.
  The user: hash followed by a space cannot occur anywhere else, so `#` can be overloaded; it makes Python-style comments usable. I also accept `#` at the end of a line (an empty comment line,
  editors strip trailing spaces) but never a `#` directly after a digit: `2#` is the start of a binary literal and `x = 2#` must stay an error instead of silently becoming `x = 2`.
  `1# comment` (glued to a number) is therefore an error. Hex literals `#ff` do not clash: the character after the hash is not a space.
  Wording (user, version 6.2): `# ` comments and `0x` literals are compatibility forms. They exist to ease the migration of existing programs and for copying code and constants
  between Ka and other languages (Python files above all); they are discouraged in new Ka programs, which should use `--` and `#ff` / `2#...`. The reference says so.
  The user asked for the inside-line form to stay on one line and said the rules were a minor issue. strip_comments() blanks comments before
  the lexer so that line numbers and columns stay right.
TAB: no special treatment (user decision, version 3). It is a character like ESC or `$`: text inside strings/comments, `unexpected character`
  elsewhere. Earlier (version 2) any TAB was an error; the simpler rule needs no code at all.
Identifiers: ASCII only. `and or not let global nonlocal input fn` are ordinary names (the words were removed from the language).
Numbers: `_` only between digits (user: no `__`, not at the start or end). Hex `#ff` (and, version 6.1, `0xff` / `0XFF`, so that constants copied from Python files work) and binary `2#1011` take all 64 bits
  and wrap to signed. A number that does not fit any form gives `bad number '...'`; the hint about `_` is shown only when there is a `_` in it, `0b101` gets the hint `2#101`
  (the first version of the message blamed `_` for every ill-formed token, e.g. `0xFFFF...`, which was wrong). Python's `0b` and `0o` are not accepted (Ka has `2#`, no octal).
  Only base 2 exists; radix 3..36 (`3#122`, `36#zzz`) is on the wish list. `#'...'` is reserved for hex byte strings.
Floats: `digits.digits`, `digits.digits e sign digits`, `digits e sign digits` (user's list); no `.5`, no `1.`, no INF/NAN literals.
  `5e3` is a float. Specific error messages for the near-misses (`1.`, `.5`, `1e`, `1.5abc`, `1.5.2`).
Strings: `'...'` = byte string, `"..."` = unicode string (user). For now both are stored as UTF-8 bytes and printed as such; they differ only in the meaning
  of `^XX` (raw byte vs. character U+00XX). The user plans real unicode strings (32-bit code points) later; print will then have to encode.
  Escape char is `^` (not `\`) so that `\` stays free (it became the `function` synonym and integer division). `^uXXXX` and `^UXXXXXX` are the user's spelling.
  Joining of adjacent literals: a newline ends a statement, so `print "a"` NEWLINE `"b"` is two statements; inside parentheses newlines are ignored,
  so `print ("a" NEWLINE "b")` joins (user's example). Since version 6.4, byte-string literals (`'...'`) are also values; unicode literals (`"..."`) remain print-only.
  The generated program calls SetConsoleOutputCP(65001) at start so that UTF-8 shows correctly; the console keeps that code page afterwards
  (restoring it was not worth the code).
  Version 6.4 byte-string values: each non-empty literal is stored in `.data` as an aligned `[u64 byte_length][bytes]` object;
  the expression value is its address. The empty string is the null pointer. Variables, parameters, return values and closure boxes already
  carry 64-bit values, so assignment/calls/returns copy only the pointer and require no special calling convention. Strings are immutable;
  no runtime allocation, freeing, reference counting or GC is needed yet. `rt_print_value_str` handles null and passes the object's
  length and contents to the existing `rt_print_str`. The checker has a distinct `str` type; it is not numeric, and string comparisons
  are deliberately not enabled yet. Unicode (`text`) literals are still printable only.
Keywords: `function` with the synonym `\` (user), `skip` (empty statement), `elif`; `fn` is gone. A one-parameter function needs no parentheses
  (`function f x: ...`, `\x: =x+1`): `function name x` is a definition, `function x:` a literal; decided by two tokens of lookahead.
Operator spelling is the user's: `+>` arithmetic shift right, `<*` / `*>` rotate, `?` and `!` for the conditional (`!` because `:` starts blocks),
  `@x` for variables of the enclosing function (temporary, user expects to redo it).


3. Statements and blocks
------------------------
- Statements end at the end of the line; `;` is optional wherever the next token cannot continue the statement (keyword, `{`, `)`, `}`, `else`).
  User: "`;` is really needed only to separate statements on the same line". A line ending with an operator, `=` or `,` continues.
- One-line bodies (`if a: b; c`) run to the end of the line and nest; `else`/`elif` bind to the nearest `if` that can still take one, also across lines.
  Alternative considered: bind by indentation. Rejected as too elaborate; braces can force the other meaning.
- `{ ... }` is an ordinary statement (user, version 3). First there was a special case "`:` followed by `{`"; the user called it a mistake and asked for the
  general rule. Consequence: in `if a: {b} c()` the `c()` belongs to the body (the body runs to the end of the line), in `if a {b} c()` it does not.
- `=` at the start of a statement is a short `return`. Function bodies have no expression form and no implicit result (`fn f(x) x*x` was removed);
  a bare expression statement that is not a call gets a warning (typical mistake `{m = 2*n; m}`).
- After the removal of `let`, `global`, `nonlocal`, `input`: no way to read input for now ("it's ok for now").


4. Expressions
--------------
Precedence (user wanted few levels, "C programmers always use parentheses"):
  - Bit operators sit between `+` and the comparisons, in C's order (`&` over `~` over `|`) but ABOVE `==` and `<`, so `a & 1 == 0` means `(a & 1) == 0`.
    The user said "like in C, I guess" about the order among them; the position relative to comparisons is my choice (Python-like) because C's
    position is a well-known trap. One table row to change if exact C is wanted.
  - Shifts and rotates are one level between `&` and `+` (as in Python/C relative to `+`).
  - Unary operators bind tighter than `^`: `-2^2` is 4 (user, version 3). `^` is right-associative (`a^b^c = a^(b^c)`, user).
  - Chained comparisons (`a < b < c`) within `== !=` and within `< <= > >=`, not mixed (user); the middle operand is evaluated once, stops at the first false link.
  - Conditional `c ? a ! b`: lowest precedence, right-associative, only the chosen branch runs. `!` followed by `=` is always `!=`.
    A function literal with a one-line body inside it needs parentheses (the body would swallow the `!`).
`^` is power after an operand and the global-variable prefix where an operand is expected (`print a ^b` is a power). Same trick for `\`: function
  where an operand/statement starts, integer division after an operand. Consequence: a function definition can no longer follow a complete statement
  on the same line without `;` (it used to, as `\` was a statement start), see version 6.
Integer power with a negative exponent is a runtime error (simplest; the real result is not an integer).
Shifts (user's spelling and rules):
  - `<<` shift left; `>>` logical (unsigned) right; `+>` arithmetic (signed) right; `<*` `*>` rotate. An arithmetic shift left has no operator: it is the same
    as `<<` (user asked; yes).
  - A count of 64 or more shifts everything out (0, or the sign for `+>`). The code compares the count with 63 (unsigned compare); x86 would otherwise
    take the count modulo 64. Rotates use the hardware behaviour, count modulo 64, which is the natural definition.
  - Negative counts (version 6, user): shift the other way (`x >> -n` is `x << n`, ...). For rotates this is automatic (modulo 64).
    Before version 6 a negative count shifted everything out.
Compound assignment `x op= e` is sugar for `x = x op e` done in the parser (`&&=`/`||=` become and/or nodes, so they short-circuit). Targets `name`, `^name`, `@name`.
  A consequence of the type rules: `x /= 2` on an int variable is an error since `/` gives a float; use `\=`.
Division (version 6, user): `/` is always float division, `\` always integer division. Before version 6 `/` truncated for ints and gave a float for floats,
  so the result type depended on the operand types; two operators make the type of each operation fixed.
Floored division and modulo (version 6.2, user: "let's do it mathematically"): `a \ b` = floor(a / b) (rounds toward minus infinity), `a % b` has the sign of `b`,
  and `a \ b * b + a % b == a` always holds for ints (for floats up to rounding, as in J and Python: (-7 \ 3.2) * 3.2 + -7 % 3.2 is -7.000000000000001); `7 % 3 == 1` and `-7 % 3 == 2` because 7 - 1 and -7 - 2 are divisible by 3. Versions 6 and 6.1 truncated toward zero (C and the
  machine instruction idiv): then `-7 % 3 == -1`, and a remainder can be negative for a positive divisor, which is rarely what a modulo is used for (indexes, wrapping, ranges).
  This is also what Python does, so numbers agree with it. Implementation: the machine division truncates; the result is corrected when the remainder is not 0 and its sign differs from
  the divisor's: the quotient becomes one less, the remainder bigger by the divisor. For floats the same correction is applied to the exact C-style fmod remainder
  (rt_fmodfloor); a zero remainder is returned as +0.0 (the sign of a zero would only be noise). Float `\` = (a - fmod(a, b)) / b minus one when the remainder was corrected,
  rounded to the nearest integer: a - fmod(a, b) is mathematically a multiple of b, but the subtraction itself can round, so the quotient may come out as 13276.999999999998;
  truncating it (versions 6 and 6.1 did) gave 13276 instead of 13277 in rare cases. A quotient outside the int range gives the smallest int (what the hardware conversion returns);
  making that an error would need a new message and a check, and explicit conversions are on the wish list anyway. Above 2^53 the float quotient is not exact.
  The tests check the identity for all pairs of small ranges, and a randomised comparison with Python's // and % (3000 cases, ints and floats) found no difference.


5. Types and the checker
------------------------
- Static, inferred, no annotations: int, float, function. A variable keeps the type of its first value; a parameter gets its type from the body and the calls;
  one signature per function (monomorphic). User: "calling fn f(a){} with an int makes it f(int), so calling it with f(f) is an error".
  Alternative: per-call polymorphism. More work, little gain (all values are one machine word anyway).
- Recursive function types are allowed (`a(a)`): no occurs check; unification skips pairs it is already comparing; messages cut cycles with `...`.
  The restriction was a limit of my first checker, not a safety rule: no int is ever called.
- Return types: all `return` expressions must agree; bare `return` and falling off the end are not checked (user: "don't deal with it for now").
  Hole: a function that returns a function on one path and falls off the end gives a null function; calling it is the runtime error "call of an unset function".
- Int and float mix only inside operators (user: "ops with int and float - convert both to float"): `+ - * % ^` give float if either side is float, `/` always float,
  `\` always int, comparisons compare as floats, `?:` promotes its branches.
  Assignment, call arguments and `return` are strict: no implicit conversion. So `x = 0` then `x = 0.5` is an error, `f(1)` and `f(1.5)` cannot both be called.
  Pros: nothing happens behind the user's back, the checker stays simple. Cons: annoying (`x = 0.0`). Relaxing assignment (int widens to float) is a one-line change
  in Checker.stmt if wanted; explicit conversions are on the wish list.
- The result type of an operator can depend on parameter types that a later call fixes, so plain unification is not enough. The checker records such
  operators as constraints (arith, eq, cond, num) and settles them when operand types become known; whatever is unknown at the end becomes int
  (Checker.step / solve / finish). The code generator needs every expression's type to choose int or float instructions, so Checker.types maps
  id(node) to the type.
- Runtime arity/not-a-function checks were removed (the checker does it). The null check of a call stays (unset function variable).
- Truth: numbers only; `0`, `0.0`, `-0.0` false, NaN true.


6. Floats
---------
- A float is the bit pattern of a double in the same 64-bit slot as an int; nothing changes for variables, arguments, results, closures.
- Zero divisor: float `/`, `%`, `\` by zero (also -0.0) is a runtime error, like ints. IEEE would give inf/nan; there are no INF/NAN literals yet,
  so the error keeps them out of normal programs. Overflow still produces inf, `inf - inf` is nan; they print as `inf`, `-inf`, `nan`.
  Comparisons are exact (user: "let it be precise for now"); with NaN everything is false except `!=`. Tolerance is on the wish list.
- `%` on floats is floored (sign of the divisor, see section 4); its core is C fmod, implemented as an exact integer shift-and-subtract algorithm (the musl algorithm)
  instead of x87 `fprem`, because the emulator (QEMU) emulates fprem approximately and the tests would then depend on emulator quality.
- `^` on floats: integer-valued exponent: x87 square-and-multiply in extended precision, rounded once (any base, negative exponents give 1/x^n).
  Fractional exponent: x87 fyl2x / f2xm1 / fscale, base must be positive (a negative base is a runtime error with its own message). 0^negative is division by zero.
- Printing (user: "some good formatting like in APL, J, maybe latest Python"): at most 15 significant digits, trailing zeros removed, `.0` kept so that a float
  never looks like an int, fixed notation for 1e-4 <= |x| < 1e15, else d.ddde+XX (Python style). `0.1 + 0.2` prints `0.3` (APL-like, hides binary noise);
  Python's repr would print 0.30000000000000004. Exact shortest-round-trip printing needs big-number arithmetic or Ryu tables: too much for now.
  The digits are made in x87 extended precision (N = round(x * 10^(14-e10)), 10^k by repeated squaring). Known limitation: when the 16th digit is very close to 5
  the 15th digit can be off by one, roughly 1 case in 10 000; the fuzz run (3000+ values, random bit patterns, denormals, boundaries) found none.
  The format is provisional (wish list: precision/width/layout control, probably as pragmas).
- The routines (rt_fmt_float, rt_fpow, rt_fmod) are machine code generated from tools/float_rt.asm by tools/build_float_rt.py (Keystone assembles single
  instructions; the script does labels and jumps because Keystone hung on larger inputs). They set the x87 control word to extended precision themselves:
  Windows starts processes with 53-bit precision, which would break the digit generation. The emulator starts with 64 bits and would hide that.
- Verification: tools/fuzz_float.py runs the routines in Unicorn against Python (format, fmod: exact; integral pow: within 1 ulp). The emulator computes fyl2x/f2xm1 only to
  about 4e-15, so fractional powers are the least verified part on real Windows; tests with fractional exponents use values whose 15 digits agree.


7. Scope, functions, closures
-----------------------------
- Globals via `^x` (user: `global x = e` is not pretty, `^x = e` is). A name cannot be both local and `^x` in one function; the user dropped the idea of
  shadowed globals ("having ^x for read/write globals and x for locals doesn't seem ok"). `^x` at the top level equals `x`. `function ^name` was refused ("too much").
- `@x` = variable of the nearest enclosing function (draft, replaced the first spelling `\x`). A first version of the idea was `nonlocal x`. The user expects to
  redo it ("we'll do later"); only one level exists.
- Named functions are hoisted (created at scope entry) and are ordinary variables: reassignable to a function of the same signature. The user considered a
  single `f = function...` form instead. Problems seen: no "main code first, helpers below" layout, call-before-definition becomes a runtime error,
  mutual recursion gets fragile, duplicate definitions are silent. The user rejected it. Open idea: make named functions real constants (no reassignment,
  direct calls without a closure lookup, a place for polymorphism); not decided. (Capital-named functions already are constants, see 8.)
- Every variable starts as 0 (frames are zeroed, the data section is zero, heap boxes are zeroed). A function variable that is 0 is "unset".
- Closures capture by reference through heap boxes; nothing is ever freed (no GC): accepted for now.
- Calls: own convention (arguments pushed left to right, closure pointer in rax checked for null, callee pops). At most 20 parameters (user: 100 is too many for humans
  and too few for splitting an array).


8. Constants (version 4, extended in version 6)
-----------------------------------------------
User's idea: an identifier of capitals (digits, `_`) is a constant: it gets its value when created and cannot be assigned elsewhere; main purpose top-level parameters;
"how is it usually done?" Languages with constants (C, Go, Rust, Pascal `const`) define them once, unconditionally, with a constant initializer; so:
- Name rule: at least one capital letter, no lowercase letters (`MAX_SPEED`, `X2`, `_N`). Parameters with such names are rejected.
- Where: directly in the statements of the program or of a function body; not inside if/elif/else/loops/blocks. Version 4 allowed only the top level; version 6
  (user: "allow them inside functions too, scope = this function") allows function bodies; the scope of a function constant is that function and the ones nested in it.
  A constant cannot be written `^X` or `@X` inside a function; a function may define a constant with the name of a global one (like any local).
- Once: any second assignment, also `X += 1`, is an error. Capital-named `function NAME(...)` counts as a constant too.
- Value: a constant expression: numbers, constants defined above, operators (also ?:), function literals. A constant can be a function that calls itself by name.
  Variables and calls are not allowed. Alternative for functions (user's hint "just check that it is not set later"): allow any expression, executed in place.
  Rejected because a nested function that runs early could then see the constant unset; with constant expressions the value does not depend on run time.
- Timing: the constants of a scope are created first, in order, when the scope is entered (program start, function entry), like named functions. So they can be read
  anywhere in the scope, also above their definition (`print X` before `X = 5` is legal). This differs slightly from "gets its value when created"; the alternative
  is a "used before definition" error for top-level reads, but functions would still need hoisting to be safe.
- Implementation: the assign node gets a sixth element True; the code generator emits these assignments at scope entry and skips them in place.


9. Known issues and limitations
-------------------------------
- Not verified on real Windows by me: the x87/SSE float routines (Unicorn only), SetConsoleOutputCP, UTF-8 console output. The user ran the test suite on Windows
  after versions 3-5 and reported everything passing.
- The 15th digit of printed floats can be off by one in about 1 case in 10 000. Fractional float powers are only checked against an emulator that is less accurate than the FPU.
- Float `\` with a quotient outside the int range gives the smallest int silently. `-9223372036854775808 \ -1` raises a hardware exception (not handled).
- The compiler stops at the first error. The unused-expression warning is deliberately simple (any non-call expression statement).
- Falling off the end of a function is not type-checked (see 5). Deep recursion (about 10 000+ levels) overflows the 1 MB stack and crashes.
- A function definition cannot follow a complete statement on the same line without `;` (version 6, see 4).
- Memory is never freed.


10. Directions and ideas (not decided)
--------------------------------------
- Strings as values (bytes and unicode as 32-bit code points), operations on them.
- Explicit conversions int <-> float, rounding, floor/ceil; INF/NAN literals; comparison with tolerance (as a pragma?); output format control.
- Named functions as constants; per-call polymorphism; relaxing the strictness of float/int assignment.
- Radix literals 3..36; `for` loops; arrays; input; modules; overflow checks as pragmas; a garbage collector.
- Debug options: AST dump, assembler listing, variable dump with types (wish list in LANGUAGE.md section 10).


11. Random numbers (version 6.3)
--------------------------------
from LANGUAGE (please put it where needed or join with the rest text)
  The generator is SplitMix64 with the initial state `#123456789ABCDEF0`, set at the start of every program: until a program sets the state itself, its random
  numbers are always the same. `?n` is the next 64-bit number modulo `n`; the float is `(next >> 11) * 2^-53 * x`, replaced by the next smaller float if it is not below `x`.

User's design: a unary operator `?x` on numbers; the algorithm is the user's C code (SplitMix64 with next_u64, rand_int64, rand_float64), translated to machine code.
- `?n` (int n > 0): next_u64 % n (as unsigned numbers), so 0..n-1. The modulo bias is accepted, as in the C code. `?1` is always 0 but still draws a number.
- `?0`: the next 64 bits as a signed int. `?m` (int m < 0): the state becomes -m and the result is 0: "half the range, not all cases, but it's ok" (a seed is
  a positive 63-bit number; for the smallest int the negation wraps to 2^63, so that case is also a valid state).
- `?x` (float x > 0.0): ((next >> 11) * 2^-53) * x, which is exact for the 53-bit part; if rounding made the result reach x it becomes nextafter(x, 0.0) (the number below x,
  i.e. one less in the bit pattern). For x <= 0.0 nothing is checked: the C code is followed literally (x = 0.0 gives 0.0, a negative x gives a number next to x, NaN gives NaN);
  the reference says "not defined". Alternative: a runtime error, not asked for.
- Determinism (user): the state at the start of every program is the constant 0x123456789ABCDEF0, so a program always gets the same numbers (useful for tests). The user plans a time() later
  and then the seed can come from the clock: "when we implement time(), we'll see". The state is 8 bytes in .data (offset 0x40), its initial value is written into the data image by build_pe.
- Parsing: after an operand `?` is the conditional operator, where an operand is expected it is the unary random operator (the same trick as for `^` and `\`). It binds like the other unary
  operators (tighter than `^`). `??5` works (the inner number is the argument). Type: the type of the operand (int -> int, float -> float), decided at compile time.
- My choices where the user said nothing: `?x` as a statement gives no "value not used" warning (it is the way to set the seed); `?` is not allowed in a constant expression (a constant must not
  depend on a generator); the three routines (rt_next_u64, rt_rand_int, rt_rand_float) are hand-assembled in ka.py like the rest of the runtime, not generated from float_rt.asm.
- Tests: tests/62_random.ka. The expected numbers come from an independent Python version of the C code, not from the compiler.
